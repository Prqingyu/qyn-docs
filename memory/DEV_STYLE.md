**开发风格原则：能用 Agent 也能用硬编码解决的问题，倾向交给 Agent，做成标准的 prompt 模板。**

**Why:** 生成的代码无法覆盖所有情况。硬编码的规则（如字符串精确匹配、精确时间匹配）会漏掉边缘情况和语义模糊。Agent 的语义理解能处理部分重叠、同义词、模糊引用等。

**How to apply:**

| 类型 | 归谁 | 例子 |
|------|------|------|
| 确定性计算 | 代码（保留硬编码） | 日期计算、ISO 周、奇偶周判断、状态过滤、过期清理 |
| 语义判断 | Agent（标准 prompt） | 时间冲突检测、任务名匹配、输入理解、分类 |

判别标准：
- 结果是**精确的、可验证的** → 代码
- 结果是**模糊的、需要理解上下文** → Agent 的标准 prompt

实现形态：语义判断做成**标准 prompt 模板**，放在 Agent 的 system prompt 或专门方法里，不要散落在 if/else 里。

**附加原则：不用代码审查 Agent 的输出结果。**
- 不写代码对 Agent 产出的语义内容做二次校验（如"安排超载了代码要拦"、"effort 数值代码要查合理性"）
- Agent 的语义输出就是结果，代码只保证**结构合法性**（JSON 能解析、字段类型对、可落盘）
- 理由：审查 Agent 的语义输出 = 用有限规则约束无限语义，这条路走不远
- 所以数据里倾向**自然语言字段**而非枚举（枚举=用代码限死 Agent 的表达，同样走不远）

**附加原则：schema 最小够用 + 可演进，不预先完备。**
- 当前结构是从用户少量例子推导的，真实使用大概率会推翻它——承认这一点
- 不为未出现的场景预留字段；够承载当下已知 + 允许未知信息流入即可
- 开放通道（键值对/自然语言字段）比完备结构重要
- schema 是"当前版本快照"不是"定稿"；承载不了就演进 + 迁移数据，不硬塞
- Agent 遇到现有结构表达不了的信息时，应**主动报告**（structure_insufficient），而不是硬塞进现有字段

**已按此原则处理：**
- 时间冲突检测（含部分重叠）→ Agent 的 `detected_conflicts` 字段
- 任务名匹配（`_task_match`）→ extract prompt 注入已知任务列表，让 Agent 语义匹配简称/同义（"论文"→"结课论文"），代码只做兜底包含匹配
- 其他确定性计算（日期/周/奇偶/状态过滤）→ 保留代码硬编码
